# Test framework refactor plan

This is the spec for a later implementation. Scenarios, step definitions, and page objects stay as they are, except for the fixes named below (ext-test relogin, the Defra ID branch that currently keys off `@browserstack`, and the five `~/node_modules` imports).

Once implementation starts, do not edit this file. The first implementation step creates `ai-revision-log.md` in the repo root. Every AI change after that is appended there: what changed, why, and which item in this plan it covers. If a decision moves, the log records the move. This plan stays as written.

Do not implement the items under "Later" or "Do not do". Do not edit `env.sh`, except to delete the unused `USER_BASIC_AUTH_TEST1` export described under Env files. It is gitignored and holds secrets. Change `env.sh.template` only. Developers copy the unsets into their own `env.sh`.

## Why

The runner mixes three choices in the same files and npm scripts:

- **Where** the system under test is (local, dev, test, ext-test, perf-test): URLs and non-secret config.
- **How** the browser is started (CDP Chrome sidecar, BrowserStack, local Chrome, local Selenium grid).
- **What** runs (Cucumber tags and feature paths: admin tool, compatibility, Defra ID stub, real Defra ID).

A script today picks all three at once. The admin tool is another suite living in this same repo, which is why the split matters. Secrets are not part of where. CDP stores them in Portal config or Portal secrets. A developer stores them in `env.sh`, which is gitignored.

## Where, how, and what

**Where** is the environment: `local`, `dev`, `test`, `ext-test`, `perf-test`. It selects URLs and other non-secret config. It does not select the browser, and it does not by itself mean "these scenarios use the stub".

**How** is the driver:

| How | Config today | Browser |
| --- | --- | --- |
| CDP sidecar | `wdio.conf.js` | Platform Chrome at `CHROMEDRIVER_URL`:`CHROMEDRIVER_PORT`, default `127.0.0.1:4444` |
| BrowserStack | `wdio.browserstack.conf.js` | BrowserStack hub. Local binary `/root/.browserstack/BrowserStackLocal` when `HTTP_PROXY` is set |
| Local Chrome | `wdio.local.conf.js` | The developer's Chrome |
| Local grid | `wdio.local.grid.conf.js` | `selenium/standalone-chrome` from `npm run local:grid:chrome:start` |

**What** is Cucumber tags plus an optional `--spec` path. The admin tool is a what. Compatibility is a what. Stub versus real Defra ID is a what.

Tags must not choose the driver. The driver config must not choose the URL or the product area.

## Defra ID stub versus the real service

In CDP, dev and test are not the same journey pointed at two hosts. Dev has the Defra ID stub. Test does not, and uses the real Defra ID service. perf-test is treated like dev for tags today.

That split is currently hidden in two places:

- `buildCucumberTagExpression` in `test/utils/cucumber-tag-expression.js` always starts from `@env_${ENVIRONMENT}`. `dev` and `perf-test` both become `@env_dev`. Any `CUCUMBER_EXTRA_TAGS` value is ANDed on. CLI `--cucumberOpts.tags` replaces the whole expression, which is why extra tags go through the env var.
- `test/step-definitions/defra-id.js` logs in via the stub when `ENVIRONMENT` is `dev`, `local`, or `perf-test`. Otherwise it uses real GOV.UK or Government Gateway. A `@browserstack` tag on a non-ext-test run also changes which user pool is used. That is behaviour, not just selection. Keep the behaviour working when the tag is renamed.

What we want: tag scenarios that need the stub, and tag scenarios that use the real service. The environment still says where the stub or the real service is. Suggested tag names, matching the existing `@env_*` style: `@defra-id-stub` and `@defra-id-real`. Apply them to existing scenarios. Do not rewrite scenario text. Update the login branch in `defra-id.js` so it follows the tag, not `ENVIRONMENT` and not `@browserstack`.

`@env_*` can remain as a where-filter during the move, but a new run must be able to choose stub versus real without encoding that in the environment name.

3. **GitHub / CI.** `.github/workflows/journey-tests.yml` calls `DEFRA/cdp-node-journey-test-suite-template/run-journey-tests`, with `compose.yml` (Chrome, mongo, redis, localstack). Do not recreate `wdio.github.conf.js` or `wdio.github.browserstack.conf.js`. Remove `test:github` and `test:github:browserstack` from `package.json`, and the README section that documents those missing files, only as part of stopping the dead scripts. BrowserStack-from-GitHub is later.
4. **CDP sidecar.** `npm test` with `PROFILE` unset, `wdio.conf.js`, sidecar on port 4444.

That script must not source `env.sh`, because the Portal image does not have that file. A local BrowserStack run is a separate script that sources `env.sh` and then uses the same config. Do not add `. ./env.sh` to the script `PROFILE=browserstack` calls.

Today `test:browserstack` forces `CUCUMBER_EXTRA_TAGS='@smoke'` and `test:browserstack:regression` forces `not @smoke`. That is the compatibility set being chosen by the how. ## Setup folder and config manager

Add one setup folder for startup shared by every how. Suggested place: `test/setup/`. Each WebdriverIO file keeps only what is different about that driver.

The config manager takes `ENVIRONMENT` and returns the URLs for it. Today those URLs are split:

- `baseUrl` is copied in `wdio.conf.js`, `wdio.local.conf.js`, `wdio.local.grid.conf.js`, and `wdio.browserstack.conf.js`.
  - ext-test: `https://waste-tracking.integration.defra.gov.uk`
  - `ENVIRONMENT=local` inside `wdio.conf.js` only: `http://waste-organisation-frontend:3000`
  - otherwise: `https://waste-organisation-frontend.${ENVIRONMENT}.cdp-int.defra.cloud`
  - the local and grid configs do not have the compose host, so `local` is not the same URL everywhere. The manager must make `local` mean the compose host for every how.
- Service URLs are JSON files: `test/support/local.config.json`, `local.zap.config.json`, `dev.config.json`, `test.config.json`, `ext-test.config.json`, `perf-test.config.json`. `beforeScenario` reads `test/support/${ENVIRONMENT}.config.json`, or `${ENVIRONMENT}.zap.config.json` when the proxy mode is `zap` (today that switch is `ZAP_PROXY_API_URL` being set). `local.zap.config.json` also holds `zapProxyExcludeRegexes`, which `onPrepare` registers with ZAP after `newSession`. Keys include `defraIdServiceUrl`, `govUKBaseUrl`, `govtGatewayLoginUrl`, `govPayBaseUrl`, `wasteOrganisationFrontendBaseUrl`, backend and Cognito URLs, and `adminUiBaseUrl`. `ADMIN_UI_BASE_URL` overrides `adminUiBaseUrl` when set. `ApiFactory` also rewrites the organisation and movement backend URLs to the ephemeral protected API host when `xapikey` is set. Keep that override.

The support JSON is not only URLs. `test.config.json` holds `govUKLogin` lists, and `ext-test.config.json` holds `defaultGovUKLogin`. `onPrepare` in each config loads that file and fills the shared-store pools (`availableGovUKUsers` and the other pools beside it). Callers must still receive the whole file. A URL helper is an extra view over it, not a replacement that drops non-URL keys.

Secrets do not go in the JSON. Passwords, API keys, basic-auth credentials, and BrowserStack keys stay in CDP secrets or local `env.sh`.

The manager also maps those environment variables to named getters, the same idea as `digital-waste-tracking-uat` `test/support/test-config.js`. A getter reads `process.env` when called (`cognitoClientId` reads `COGNITO_CLIENT_ID`, `proxyMode` reads `PROXY_MODE`, and the same for the other variables the suite already uses). The value is not copied into a support JSON file and is not stored on the object. Shared setup uses the getters: proxy mode, `MAX_INSTANCES`, hooks, and `ApiFactory`. The Cucumber world still receives the whole JSON file and `process.env`. Existing steps keep `this.env.SOME_VAR` and `this.testConfig.someJsonKey`. Moving those call sites onto the getters is later.

The same manager can later hold more non-secret per-environment test data. Do not move fixtures, spreadsheets, or the shared-store pools in this work. Leave the loaded config object able to grow those fields without a second mechanism.

Also move into the setup folder the duplicated non-driver settings: Chrome arguments and page-load timeouts from the sidecar config, Cucumber options, Allure and spec reporters, and the hooks listed below. Do not merge BrowserStack's multi-browser capability list into the sidecar Chrome args.

Timeouts that differ by how must stay different. Do not copy one config's numbers onto the others.

| Setting | Sidecar `wdio.conf.js` | Local and grid | BrowserStack |
| --- | --- | --- | --- |
| `waitforTimeout` | 20000 | 10000 | 120000 |
| `cucumberOpts.timeout` | 60000 | 60000 | 180000 |
| page load / script | 60000 / 30000 | (driver default unless set) | 120000 / 120000 |
| `connectionRetryTimeout` | 120000 | 60000 | 120000 |

`connectionRetryTimeout` is 120000 in `wdio.conf.js` and `wdio.browserstack.conf.js`, and 60000 in the two local configs. 120000 is the WebdriverIO default. The sidecar used to be 6000, which aborted `POST /session` while the driver was still coming up. Keep 120000 for the sidecar and BrowserStack. Do not lower it when the configs share code. `connectionRetryCount` is 3. It only repeats connection errors (`ETIMEDOUT`, `ECONNRESET`, and the other codes in Webdriver's list). An abort from `AbortSignal.timeout` is not in that list, so the count does not multiply the 120s clock. Do not raise the count to "make session create wait longer".

## Parallel instances

Sidecar, local grid, and BrowserStack take the number of parallel workers from config. Suggested env var: `MAX_INSTANCES`, default `1` when unset, so a run that does not set it keeps today's single worker. Apply that value to the runner `maxInstances` and to any per-capability `maxInstances` in that how. Local Chrome uses the same value.

Each worker still has its own session and still starts each later scenario on a clean browser. Raising the number does not share cookies or config across workers. The platform has to provide that many browsers. This repo does not add Chrome to the image, and it does not change the Selenium image pin. A sidecar with one slot will sit on `POST /session` until `connectionRetryTimeout` if the number is higher than the slots Portal gave it.

## Proxy

There are two uses of the HTTP proxy, and one URL.

- **CDP egress.** CDP sets `HTTP_PROXY` so the test container can reach the outside world (BrowserStack, and any other call that has to leave the platform). `wdio.browserstack.conf.js` calls `bootstrap()` from `global-agent` only inside `if (process.env.HTTP_PROXY)`, and sets `global.GLOBAL_AGENT.HTTP_PROXY`. When `HTTP_PROXY` is set, BrowserStack Local uses `binarypath: /root/.browserstack/BrowserStackLocal`, `proxyHost: localhost`, `proxyPort: 3128`.
- **ZAP on GitHub / CI.** The same variable points at ZAP so that run's traffic is observed. ZAP is the proxy for Compose CI. It is not another how and not another where.

If `HTTP_PROXY` is unset, do not proxy and do not call `bootstrap()`. If it is set, use it. The mode says which traffic.

This repo currently splits the decision across three variables. The browser capability in `wdio.conf.js` prefers `ZAP_PROXY_URL`, then `HTTP_PROXY`. API clients use `ZAP_PROXY_API_URL ?? HTTP_PROXY` (`test/utils/apis/api-factory.js`). `beforeScenario` loads `test/support/${ENVIRONMENT}.zap.config.json` when `ZAP_PROXY_API_URL` is set. `onPrepare` opens a ZAP session only when `ENVIRONMENT` is `local`, `ZAP_PROXY_URL` is set, and the tags do not already include `@zap`. `ZapApi` is constructed with `httpProxy` null. `npm run test:zap` runs the sidecar with `@zap`. The scenario is `test/features/waste-organisation-frontend/security/AnalyseZapReport.feature`.

Follow the sibling repo `digital-waste-tracking-uat` (the directory above this one). Its decision lives in one place:

- `test/support/test-config.js` reads `PROXY_MODE` as `off`, `cdp`, or `zap`. Any other value throws.
- `off` ignores `HTTP_PROXY`.
- `cdp` proxies the calls that have to leave the platform (external calls, for example Cognito). Internal service calls stay direct. CDP sets `HTTP_PROXY` itself.
- `zap` proxies internal and external calls so ZAP sees the flow. `HTTP_PROXY` is the ZAP proxy and the ZAP REST API URL. `ZAP_API_KEY` authenticates that API.
- `test/apis/api-factory.js` applies the mode once and constructs `ZapApi` only when the mode is `zap`.
- Scan and gate are two runs. The scan uses `PROXY_MODE=zap` and writes `zap-report/` (`zap.json`, `zap.html`, `alerts-summary.json`). The gate uses `PROXY_MODE=off` and fails when high alerts are not zero. `.github/workflows/integration-tests.yml` sets `HTTP_PROXY: http://localhost:8080`, `PROXY_MODE: zap`, `ZAP_API_KEY: local-zap-key`. The Compose service is `ghcr.io/zaproxy/zaproxy:stable` on port 8080 in `shared-compose/compose.yml`. That repo's `test/README.md` says this is for Docker Compose CI on internal HTTP URLs, not for CDP HTTPS endpoints.

Put the same decision in this repo's setup config. Browser capability, API clients, and the choice of `*.zap.config.json` all read it. Drop `ZAP_PROXY_URL` and `ZAP_PROXY_API_URL` once that is in place. The ZAP REST client keeps talking to ZAP directly, so its own API calls are not sent back through the proxy. Open the ZAP session when the mode is `zap`. Keep `AnalyseZapReport.feature`, driven by that mode.

This repo's `compose.yml` and `.github/workflows/journey-tests.yml` do not start ZAP. When the GitHub run should scan, add the UAT Compose service and set `HTTP_PROXY`, `PROXY_MODE=zap`, and `ZAP_API_KEY` the way that workflow does. The gate stays a second step with `PROXY_MODE=off`.

Do not import `undici` from a WebdriverIO config, and do not call `setGlobalDispatcher`. Webdriver sends the session `POST` with a duplicated `Content-Length`. undici 7 rejects that when it is the global dispatcher. Webdriver and the BrowserStack service each build their own proxy from `HTTP_PROXY`. Leave `@wdio/*` on 9.29.0 and `undici` on 7.30.1.

## Clean browser between tests

Every test starts on a clean browser. Cookies, storage, and login from the previous test must be gone. Config for one test must not bleed into the next. Parallelism is the `MAX_INSTANCES` setting above. It does not relax this. Workers do not share a browser.

Today all four configs call `browser.reloadSession()` in `beforeScenario` when `browser.sessionId` is set. The worker creates the session in `_initSession` before Cucumber starts, so the first scenario of a file also reloads, which is a second `POST /session` for a browser that is already empty. Later scenarios in the same file share that worker, so they do need a new session. `UKPermitPage.browserReloadSession` is the same call for a relogin inside a scenario.

What we want: keep a clean browser between scenarios. Skip `reloadSession()` only on the first scenario of a worker, because that session is already new. A relogin inside a scenario still reloads, then repeats the ext-test basic-auth check. Do not replace this with a cookie-clear helper, a raw HTTP delete of leftover sessions, or a Webdriver client that lists sessions on the driver. A killed run can leave a Chrome holding the sidecar's only slot, and the next `POST /session` then waits out `connectionRetryTimeout`. That is known. Do not add a pre-session deleter in this work.

## Report

`afterStep` screenshots a failed step. `afterScenario` screenshots every scenario, including passes. Allure is configured with `disableWebdriverScreenshotsReporting: false` and `outputDir: allure-results`. `onComplete` in `wdio.conf.js` writes `FAILED` when `results.failed > 0`. The comment there says the file is required for Portal status. `entrypoint.sh` turns that file into a non-zero exit after the report is published.

CDP screenshots have not been visible in the results. A worker that dies before Allure flushes also omits that feature from the published report, so the report can look greener than the pack. Do not synthesise Allure results for a worker that wrote none. Do not add a missing-results backfill.

What we want now: stop taking a screenshot for a scenario or step that passed. Keep the failure screenshot. Keep the `FAILED` file and the entrypoint check. A failure WebdriverIO actually recorded must still be in the published report. Finding out why an already-taken CDP screenshot does not appear is later, after passes are no longer screenshot.

## Module paths

`jsconfig.json` is the editor config. Node does not read it. WebdriverIO resolves imports with `execArgv: ['--loader', 'esm-module-alias/loader']` in all four configs, and that loader reads `package.json` `aliases`:

- `~` → `.`
- `page-objects` → `test/page-objects`
- `components` → `test/components`

What the suite actually imports:

- `page-objects/page` (no `.js`), from page objects only, for the `Page` class. Step definitions and `test/utils/page-registry.js` use relative paths such as `../page-objects/....js`.
- `~/node_modules/@wdio/globals/build/index` for `browser`, in five files that already import `$` from `@wdio/globals`: `my-account-home.page.js`, `manage-api-code.page.js`, `pay-service-charge.page.js`, `review-service-charge.page.js`, `service-charge-payment-details.page.js`. Nothing else uses `~/`.
- `components` is imported nowhere. `test/components` does not exist. ESLint does not read `jsconfig.json`.

The sibling repo `digital-waste-tracking-uat` is the guide. Its `jsconfig.json` is `target` `es2024`, `module` and `moduleResolution` `nodenext`, `checkJs` and `allowJs`, and `paths` of only `~/*` → `./*`, with `include` limited to the JS it typechecks. Its `package.json` `aliases` is only `~` → `.`. Jest maps `^~/(.*)$` to `<rootDir>/$1`. Imports look like `~/test/support/helpers/auth.js`, with the `.js` extension. It has no `page-objects` or `components` alias.

Bring this repo's `jsconfig.json` in line with that file: `es2024`, `nodenext`, `checkJs`, `allowJs`, and `include` of `test/**/*.js` plus the `wdio*.conf.js` files. Paths are `~/*` → `./*`, plus `page-objects/*` → `./test/page-objects/*` so the editor matches the loader. Drop `components/*`. Drop `baseUrl` unless the editor will not resolve those paths without it; the UAT file does not set it. Keep the `page-objects` alias in `package.json`, because page objects import `page-objects/page` and the loader is what makes that work. Remove the `components` alias from `package.json`.

Change the five `~/node_modules/@wdio/globals/build/index` imports to `browser` from `@wdio/globals`, on the import those files already have. Do not switch the suite over to `~/test/...` imports. New imports stay relative and include `.js`, which is what the step definitions already do. Leave the `esm-module-alias` loader on the four WebdriverIO configs.

## Notes

Clean up notes in the test code and the WebdriverIO configs.

A note that explains why something is the way it is (the proxy, the session timeout, the `FAILED` file, why dev and test differ) goes into a Cursor rule, or into an existing doc if a person needs to read it without a chat. It does not stay as a paragraph in the source. The stock WebdriverIO scaffold comments (the "Runner Configuration" banners and the commented-out examples) go. They are not context.

A method may keep a short note: what it does, in a line or two. Parameters only when the name does not say it. No history, no "see the other config", no essay.

This checkout has no host `npm`. Commands go through Docker, using the project image. That is local to this machine. Record it in a Cursor rule so a later chat runs `npm` the same way. Do not add it as an npm script. Do not make it a README requirement for other developers. Do not print or commit `env.sh`.

Interactive alias:

```bash
alias dwtnpm='docker run --rm -it --network host -v "$PWD:$PWD" -w "$PWD" --entrypoint "" "$(docker build -q .)" npm'
```

From a non-interactive shell, drop `-it` and pass the `npm` arguments after the image:

```bash
docker run --rm --network host -v "$PWD:$PWD" -w "$PWD" --entrypoint "" "$(docker build -q .)" npm <args>
```
